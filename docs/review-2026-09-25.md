# Code review, 2026-09-25

A full read of `main` at commit `f9438c4`: the server (`server/*.js`,
`server/schema.sql`, the colour database SQL and scripts), every browser
script in `src/`, the three form pages, and the tools' entry points.
`styles.css` was read for structure only.

Overall the code is careful. The server validates everything it stores,
enforces the important rules inside single SQL statements and `CHECK`
constraints, fails closed, and keeps secondary failures (mail, colours, 3D)
from affecting primary ones. The findings below are the exceptions. None of
them loses data or exposes customer information.

Severity: **P2** is a real issue with limited impact; **P3** is minor or a
hardening suggestion.

## P2: a stale 3D download can mark the viewer as failed while the retry works

`src/carVisual.js:813` (`retryOrFail`), with `onModelError` at `:842`.

When the first model download stalls, the watchdog starts attempt 2 with a
fresh URL. Attempt 1 is not cancelled (three's loader cannot be). If attempt 1
**later errors** (for example the stalled connection is finally reset), its
`onModelError` calls `retryOrFail()`. By then `attempts` is 2, so it sets
`loadFailed = true`, shows the error text, calls `onLoadError()` (the wizard
opens its checklist), and `clearStallTimer()` removes attempt 2's watchdog.
The same happens the other way round if attempt 2 fails fast while attempt 1
is still slowly arriving.

If the surviving attempt then succeeds, `onModelLoaded` shows the car and
hides the overlay, but `loadFailed()` stays `true`, so the next time the
customer returns to step 3, `ensureCar3D()` destroys the working viewer and
downloads the model again.

**Fix:** give each attempt an id, and in the error handler ignore any attempt
that is not the latest unless no other attempt is still in flight; only clear
the watchdog for the current attempt; and reset `loadFailed` in
`onModelLoaded`.

## P2: one client can switch the colour finder off for everyone for a day

`server/server.js:685` (`colourBudget`) and `:1465-1476`.

`colourBudget()` increments the process-wide daily counter **before** it
checks the per-IP daily count, and `handleColours()` calls it **before** the
per-minute `rateLimit()`. So every request counts toward the global 60,000
ceiling, including requests that are then refused with `429` for exceeding the
per-IP or per-minute limit. A single address sending 60,000 cheap requests
(each answered `429` in microseconds, with no database work) exhausts the
ceiling, and the finder answers `503` to every visitor until the 24-hour
window resets. The page falls back to its 777 local colours, so sales continue,
but with a much smaller catalogue.

**Fix:** check the per-minute limit first, then the per-IP daily count, and
only increment the global counter for requests that pass both.

## P2: the stored paint price is whatever the client sent

`server/server.js:459` (`validatePaintOrder`), `:1665-1667`.

`price` is accepted as any integer from 0 to 100,000 and stored; `finish`
(which multiplies the price) is also taken from the client. The schema
comment says the column is "what the page showed … so that the counter knows
what was promised on screen", and the shop's table and email show it as
«Precio en pantalla». A modified request can therefore record «S/ 1» as the
promised price for a gallon of tri-coat, and the counter has no way to tell.
The server already loads `src/paints.js` and could compute
`paints.price(size, finish) * units` itself.

**Fix:** compute the price on the server and ignore the client's, or store both
and flag a mismatch.

## P3: «Quitar nota» fails silently on any error

`src/staff.js:2285` and `:2394-2437`.

The card menu's «Quitar nota» calls `putNote(worker, "", card)` without the
fourth argument, `save`. If the request fails (network error, `403`, `503`),
the `.catch` handler calls `reopen()`, which does `save.disabled = false` on
`undefined` and throws a `TypeError`. `setError()` on the next line never
runs, so the boss gets no message, and the browser logs an unhandled
rejection.

**Fix:** guard `reopen()` with `if (save)`.

## P3: the daily mail ceiling can be exhausted by one address

`server/mail.js:867` (`withinDailyCap`) and `server/server.js:1633`.

The public form allows 10 requests a minute per IP, and each request queues two
messages against a shared daily total of 280 (and 120 customer
confirmations). One address can use up the day's mail in about 14 minutes,
after which real customers get no confirmation and the shop gets no notice
until midnight UTC. The requests themselves are still stored and visible in
the panel. The comments present the ceiling as a deliberate trade-off against
using up Brevo's quota; a per-IP **daily** limit on the public POST routes
would narrow it.

## P3: picking a finish mutates the finder's cached row

`src/paintings.js:500-509`.

The finish chips write `state.colour.finish`. When the colour came from the
finder, `state.colour` is the same object as the row in `finderState.rows`, so
the grid tile's metadata changes too, and re-picking that tile later brings
back the corrected finish with `finishGuessed: true`. Harmless in practice,
but surprising. Copy the row in `pickFromFinder()` and `showColour()`.

## P3: a walk-in cannot be registered if the 3D viewer fails

`src/staff.js:2814` (`mountIntake3d`) and `:2956`.

The wizard has a plain checklist for when the 3D viewer, three.js or the model
fails to load. The walk-in form has none, and at least one panel is required,
so a failure leaves the boss unable to register the car (the error says to
choose the silhouette again to retry). Reusing the wizard's checklist, built
from `AUTOCOLOR_PARTS.BY_VEHICLE`, would close the gap.

## P3: a delivered or cancelled paint order can still be redefined

`server/db.js:372` (`definePaintOrder`).

The rule only checks `method = 'in_person'`, so the boss can change the colour,
tin and price of an order that is already `entregado` or `cancelado`. Probably
fine for a single trusted user; worth a status check if the price record
matters.

## P3: no security headers on responses

`server/server.js` (`sendJson`, `serveStatic`).

No `Content-Security-Policy`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy` or `frame-ancestors`. The session cookie's `SameSite=Strict`
already stops a framed panel from being logged in, so the practical risk is
low. A strict CSP (the pages have no inline scripts or event handlers, only
the two import maps, which can be hashed; `index.html` has six inline `style`
attributes) and `nosniff` are cheap hardening.

- The header of `server/server.js` (`:6-21`) lists nine routes; there are 23.

- «383 makes», «68,717 colours» and «693,636 associations» appear in

  still is, every merge to `main` publishes the whole repository statically,
  including `server/` and the panel page. Worth checking in the repository
  settings.

## Checked and found correct

Things that looked risky and are handled:

- Path traversal, dotfiles, case tricks and `%` decoding in `serveStatic`.
- `X-Forwarded-For` parsing from the right, IPv6 `/64` bucketing, and
  IPv4-mapped addresses.
- Constant-time password comparison, and login checks that always run both
  halves.
- CSRF on staff routes (the `SameSite=Strict` cookie) and on public POSTs
  (JSON content type plus `Origin` check).
- Race-free occupancy and status changes (single statements on locked rows,
  plus `CHECK` constraints).
- HTML escaping of every user-typed value in the emails, and prototype-key
  lookups (`constructor`) in label maps.
- The colour database's privilege model, TLS enforcement, and in-function
  limits.
- The mail queue's retry, permanent-failure and duplicate-avoidance logic.
- Idempotency and ordering of `schema.sql`'s migrations.
